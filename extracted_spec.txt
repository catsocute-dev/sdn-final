Subject: SDN302  |  Semester: FALL 2026 |Internet Access: Yes
1. Overview
You will build ReadLog, a small web app where each person tracks their own reading sessions: which book, how many minutes, what genre, and when — with a few sessions marked as favorites, and a live summary of minutes read by genre. The project will be built with: a Next.js project (App Router) that exposes its own REST API (Route Handlers), Prisma as the ORM, PostgreSQL hosted on Supabase as the database, your own email/password authentication, and a deployment on Vercel.
This exam describes what the app and its API must do, not how to code them. How you structure the code is up to you, as long as the routes, the visible texts, the data-testid names, and the API request/response shapes in this document are exactly as written — the API is graded by calling it directly, and the web pages are graded with an automated browser, so both must match this spec precisely.
2. The application
2.1 Setup
A Next.js project (App Router, TypeScript) with Tailwind CSS and ShadCN UI (components.json in the project root, at least two ShadCN components actually used).
It must build with npm install followed by npm run build using only three environment variables: DATABASE_URL, DIRECT_URL and AUTH_SECRET. No connection string or secret may be written directly in the code.
Your package.json build script must run Prisma's client generation before building, e.g. "build": "prisma generate && next build", so a fresh checkout builds without extra manual steps.
In your Supabase project: use its PostgreSQL database only (via Prisma). Create one test account for the grader by registering it through your own app's Register page or API before you submit — do not create it directly in Supabase's dashboard, since the grader logs in through your app, not through Supabase.
Run your migrations against that Supabase database before you submit (e.g. npx prisma migrate dev, or migrate deploy) and commit the prisma/migrations folder, so the live database already has the right tables when the grader tests your deployed app.

Security rules (enforced in your API code, not only in the UI):
Every /api/reading-logs* route requires a valid, logged-in session. With no session, or an invalid/expired one, it returns 401 and touches no data.
A user may only read, add, change, or delete their own reading sessions. The server must derive the owner from the logged-in session — never from a userId or ownerId sent in the request body or query string. A request that sends someone else's id in the body must be ignored, not honored.
Build every Prisma query through its query builder (where, data, etc.) — never by concatenating raw SQL strings with user input.
Never commit a real DATABASE_URL, DIRECT_URL, or AUTH_SECRET value to the repository, and never log passwords or password hashes.
2.3 Authentication
Implement your own email/password authentication (no NextAuth.js or Supabase Auth required for this exam — a custom API is enough, implementing JWT with your own API). On successful login, your API must set a session as an HttpOnly cookie named session_token so the grader's automated tests can log in once and reuse the same session for every later request, exactly like a browser would.
Required auth endpoints:
POST /api/auth/register — body { email, password, confirmPassword }. Creates a new User (password stored only as a bcrypt hash) and returns 201 with { id, email }. Does not log the user in.
POST /api/auth/login — body { email, password }. On success, sets the session_token cookie (HttpOnly) and returns 200 with { id, email }. On a wrong password or unknown email, returns 401 with { error: "Invalid email or password" } and no cookie is set.
POST /api/auth/logout — clears the session_token cookie and returns 200. A later call to GET /api/auth/me must then return 401.
GET /api/auth/me — returns 200 with { id, email } for the logged-in user, or 401 with { error: "Unauthorized" } if there is no valid session.
2.4 Reading Log API
Required reading-log endpoints, all requiring a valid session (see Security rules above):
Every endpoint below returns one reading session — or a list of them — shaped exactly like this (field names and types fixed; your own id format is fine):
{
  "id": "cls9f2q1e0000...",
  "bookTitle": "Atomic Habits",
  "minutesRead": 40,
  "genre": "Non-Fiction",
  "note": "Chapter 3",
  "favorite": false,
  "readOn": "2026-10-20",
  "createdAt": "2026-10-20T08:15:00.000Z"
}
All error responses, from any endpoint in this document, are shaped the same way:
{ "error": "<exact message>" }
GET /api/reading-logs — returns only the current user's reading sessions as a JSON array of the shape above, ordered by readOn descending (most recent first); ties broken by bookTitle, alphabetically, case-insensitive. Accepts optional query parameters that filter the result: ?genre= (one of the five genres), ?favorite=true, and ?q= (matches bookTitle OR note, case-insensitive, surrounding spaces ignored). The parameters combine — every one that is given must match.
GET /api/reading-logs/summary — accepts the same optional genre/favorite/q query parameters as the list, and returns a summary computed only over the sessions that match them, shaped like this:
{
  "count": 5,
  "favoriteCount": 2,
  "totalMinutes": 180,
  "breakdown": [
    { "genre": "Fiction",     "count": 3, "total": 120 },
    { "genre": "Non-Fiction", "count": 2, "total": 60 }
  ]
}
breakdown has one entry per genre present in the matching set, ordered by total minutes descending; equal totals are ordered Fiction, then Non-Fiction, then Sci-Fi, then Biography, then Other. With nothing matching, count/favoriteCount/totalMinutes are 0 and breakdown is an empty array.
POST /api/reading-logs — body { bookTitle, minutesRead, genre, note?, readOn }. On success returns 201 with the created reading session (the shape above, including its id). Validation errors return 400 with the error shape above, using the exact messages from the table in section 2.5. A duplicate (same bookTitle, minutesRead and readOn already saved by this user) returns 409 with { "error": "Duplicate reading session: a reading session with the same book title, minutes and date already exists" }.
PATCH /api/reading-logs/:id — body is any subset of { bookTitle, minutesRead, genre, note, readOn, favorite }; used both for editing a field and for toggling the favorite. Returns 200 with the updated reading session (the shape above). The same validation and duplicate rules as POST apply to any field being changed. An id that does not exist, or belongs to another user, returns 404 with { "error": "Reading log not found" } — a user must never be able to tell, from the response, whether a given id exists for someone else.
DELETE /api/reading-logs/:id — deletes the reading session if it belongs to the current user and returns 200 with { "success": true }. An id that does not exist, or belongs to another user, returns 404 with { "error": "Reading log not found" }.
2.5 Pages and what they do
Home — / (public)
A header with the app name and, when logged out, a Login button and a Register button. Below it a title (home-title, text ReadLog) and a short description of the app, with at least three feature cards (for example "Log every session", "Sort by genre", "See minutes read").
When logged in the header instead shows the user's email, a link to the reading log page and a Logout button. After Logout the header is back to the logged-out version, and a later GET /api/auth/me returns 401.
Register — /register  and  Login — /login
Forms with your own messages, not the browser's (add noValidate); nothing is shown before the first submit; an error disappears when its field becomes valid. Register has email, password and confirm password; Login has email and password.

B. The list.
All the user's reading sessions as returned by GET /api/reading-logs (most recent readOn first, ties by bookTitle). Each session (reading-log-item) shows its book title, minutes read, genre, date, a favorite/star toggle (a button that is "on" for favorited sessions) and a Delete button. Toggling the favorite and Delete call PATCH and DELETE and the item updates at once; after a page refresh the list is exactly the same. When there is nothing to show, display reading-logs-empty with the text No reading sessions found instead of the list.
C. Filters, search and summary.
A genre filter (All, or one of the five genres), a "favorites only" checkbox, and a search box that keeps only sessions whose book title or note contains the typed text (not case-sensitive, surrounding spaces ignored). They combine, and update the list immediately (no button to press) by calling GET /api/reading-logs and GET /api/reading-logs/summary again with the matching query parameters. A Clear button resets all three. When a session stops matching because of a change (for example it is un-favorited while "favorites only" is on) it disappears from the list at once.
The summary always describes the sessions currently shown: reading-log-count (plain integer), favorite-count (plain integer), total-minutes (plain integer), and genre-breakdown with one breakdown-row per genre that appears — highest total first (ties: Fiction, then Non-Fiction, then Sci-Fi, then Biography, then Other) — each row showing breakdown-name, breakdown-count and breakdown-total.
2.6 Shared state
The reading sessions are loaded once after login and kept in React Context, so the form, the list, the filters and the summary all use the same data without passing it down as props. After logout (and when another person logs in) the previous person's sessions must disappear from memory and from the screen.
2.7 Look and feel
At a phone width of 375 px there is no horizontal scrolling and the form and list are readable; at 1280 px the form and the summary can sit next to the list. Use Tailwind CSS and ShadCN UI (Button, Card, Input, Label … at least two used).
